- (note) Why: private trip-journal logbook for a small group of friends (area -> sector -> climb -> ascent), alternative to public crowd-sourced crag databases (thecrag/27crags/Mountain Project) and gym tick-lists. Source: README.md.
- (capability) CAP-1 intent: A user can create/view/edit/delete climbing areas (name, description, how-to-get-there, comment, personal rating, map location captured via browser Geolocation). success: an authenticated user creates an area with a GPS-captured location and it appears on the map for other users. Source: apps/api/src/routes/areas.ts, ARCHITECTURE-SPINE AD-1.
- (capability) CAP-2 intent: A user can create/view/edit/delete sectors within an area (name, description, notes, rating, optional map location). success: a sector created under an area is listed under that area and visible to other users. Source: apps/api/src/routes/sectors.ts.
- (capability) CAP-3 intent: A user can create/view/edit/delete climbs (routes or boulders) within a sector, with free-text difficulty grade, personal rating, description, and free-form style tags (crimpy, slab, powerful, sketchy, endurance, ...). success: a climb created under a sector shows its tags and difficulty when viewed, and can be filtered/found by tag. Source: apps/api/src/routes/climbs.ts, tags.ts, README feature list.
- (capability) CAP-4 intent: A user can log an ascent of a climb as flash, redpoint, project, or todo (spotted but not tried), with attempt count, notes, and date. success: a logged ascent appears in that user's log for the climb, and only that user can edit/delete it. Source: apps/api/src/routes/logs.ts, ARCHITECTURE-SPINE AD-13.
- (capability) CAP-5 intent: A user can attach photos or videos to an area, sector, climb, or log entry. success: an uploaded photo/video is retrievable and displayed against the entity it was attached to; deletion follows the ownership rule for that entity type (shared-editable vs per-owner). Source: apps/api/src/routes/media.ts, lib/storage.ts, ARCHITECTURE-SPINE AD-13 (extended).
- (capability) CAP-6 intent: A person can register an account (email/name/password) and log in/out via a session cookie to use the app. success: a registered user can log in, stay logged in across page loads (session probe), and log out, clearing the session. Source: apps/api/src/routes/auth.ts.
- (capability) CAP-7 intent: A user can switch the UI language between German (default), English, and French at any time. success: switching language changes all visible UI text, including localized error messages mapped from stable Problem Details error codes, without a page reload losing state. Source: brainstorm-intent.md, ARCHITECTURE-SPINE AD-11.
- (constraint) Self-hosted, small fixed group of users, not a public/multi-tenant service - bends away from scalability, invite-flow, and admin-approval design work. Source: README.
- (constraint) SIX Docker Hub org-wide Registry Access Management policy blocks postgis/postgis and minio/minio images - infra must use postgres:18 and cleanstart/minio instead (already reflected in docker-compose.yml). Source: docker-compose.yml comment.
- (constraint) v1 is online-only by decision - no offline local queue/sync for new sectors/images. Bends the frontend data layer away from a local-first sync engine. Source: brainstorm-intent.md, ARCHITECTURE-SPINE Deferred.
- (constraint) Whole project is implemented by an AI coding agent rather than hand-coded - stack/tooling choices favor official, well-documented, agent-legible paths (official CLIs, official OpenAPI/i18n packages) over community starters or exotic alternatives, even when the latter might be marginally more featureful. Source: brainstorm-intent.md.
- (non_goal) No public/crowd-sourced climbing database features (route democracy, public search, community moderation) - explicitly the opposite of what this app is. Source: README Why section.
- (non_goal) No native mobile app or app-store distribution, no PWA-as-native shell, for v1. Source: brainstorm-intent.md.
- (non_goal) No offline-first support (local queue-and-sync while offline) for v1 - deferred, not rejected. Source: brainstorm-intent.md.
- (non_goal) No pagination or advanced filtering beyond simple equality query-param filters, for v1. Source: ARCHITECTURE-SPINE Deferred.
- (non_goal) No backend-side localization/Accept-Language handling - all UI language lives in the frontend. Source: ARCHITECTURE-SPINE AD-11.
- (note) Success signal: from a fresh self-hosted deploy, two friends can each register and log in, one adds an area+sector+climb with a GPS-captured location, the other logs an ascent of that climb with a photo attached, and both see each other's areas/sectors/climbs/logs/photos - all navigable in German, English, or French.
- (assumption) Assumed 'small group of friends' means roughly 2-10 users, which is what makes the shared-editable ownership model (any authenticated user can edit any area/sector/climb) reasonable rather than risky. Not explicitly sized by the user.
- (question) Open: registration (POST /api/auth/register) currently has no invite code or admin-approval gate - anyone who can reach the instance can create an account. Acceptable given 'self-host it and invite who you want' (i.e. network-level privacy is the real gate), or should there be an invite/approval step? Not explicitly confirmed.
