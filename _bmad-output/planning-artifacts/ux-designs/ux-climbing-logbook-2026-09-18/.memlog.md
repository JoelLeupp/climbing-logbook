- (decision) Sources confirmed: SPEC.md (primary), glossary.md, ARCHITECTURE-SPINE.md (all from _bmad-output/specs/spec-climbing-logbook and companion). No PRD exists; SPEC.md substitutes.
- (decision) Working mode: Coaching path. Stakes: consumer-grade (full accessibility floor, polish, edge cases) despite being a hobby/small-group project - explicit user choice, not the hobby default.
- (decision) Overall feel: smooth, fresh, simple, clean, smooth transitions, professional/polished ('taste') - user is a professional programmer with high visual standards. Media (photos) should be presented well/prominently.
- (decision) Multi-surface, both matter: at the crag on a phone (log ascents, save routes/boulders to try later); at home on a bigger screen (browse trip photos, plan next trip, add a new sector/routes to try from home). Form-factor resolves to: responsive web, mobile-first for on-site logging, desktop-capable for home planning/browsing - not one primary surface.
- (decision) Light gamification: an achievement/badge icon (e.g. a trophy) for flashing a route (first-go send). This is new scope beyond SPEC.md's 9 capabilities - not yet a formal capability, flagged to feed back to bmad-spec at close.
- (decision) Rating: user can rate route/area/sector (already schema-supported via personalRating - this is a UX surface requirement on existing data, not new).
- (decision) Personal statistics page: total climbs this year / overall, grouped by grade. Grading standard requested: French/Fontainebleau scale (5a, 5b, 5c, 6a, 6a+, ... 7c, 8a), one unified ordered scale for both routes and boulders. This conflicts with packages/db/src/schema.ts's current free-text difficulty field (deliberately free text because 'grading systems differ per kind') - real fork to resolve: keep free text (statistics do best-effort parsing) vs. switch to a constrained ordered French-grade enum (trivial, reliable grouping, but a schema change). Flagged, not yet decided.
- (decision) New capability: app-content search, available from anywhere (e.g. a search bar overlaying the map), searching across area/sector/climb name and difficulty. Results highlight on the map or filter it to show only matches. Distinct from AD-14's geocoder place-search (which finds real-world locations to pan to) - this searches the app's own data. Not in SPEC.md's 9 capabilities - flagged to feed back at close.
- (decision) IA: a view toggle between the map view and an alphabetically-sorted, collapsible list view of areas/sectors on one scrollable page - two views over the same data, user-switchable.
- (decision) Map click semantics clarified: clicking an empty/unused point creates a new area there (CAP-1); clicking an existing area marker opens that area's detail view, from which sectors are added; from a sector's detail view, climbs (routes/boulders) are added. Resolves CAP-1's earlier vague 'click to create.'
- (note) Geocoder should resolve villages/regional names, not just addresses (like Google Maps) - largely already satisfied by AD-14's Nominatim choice (resolves localities/regions natively); user flagged fine-tuning this as an acceptable future-polish item, not a v1 blocker.
- (decision) Media upload v1: drag-and-drop file picker only. On-site camera capture is a future/nice-to-have, not required for v1.
- (decision) Auth/invite/register screens: lean and simple, good first impression - not feature-dense. Standard invite-link flow (best-practice pattern: visit invite link/paste code, prefilled context, register, land in the group), smooth and simple.
- (decision) Dark mode: explicitly not needed/wanted for v1.
- (decision) Journey (at the crag, mobile) - Joel: if a route he wants isn't set up yet, he opens the app and either searches for the area or it's auto-recommended/opened because geolocation identifies he's near it. New capability nuance: geolocation-based 'you're near area X' auto-suggestion, beyond just centering the map.
- (decision) Journey continued: selects the sector he's at, taps 'Add new route', enters name, difficulty (French grade enum), optional tags (overhang, pockets, ...), optional description, optional length. 'Length' is a new field not currently in packages/db/src/schema.ts's climbs table - flagged to feed back.
- (decision) Journey continued: on a route's detail view, action buttons Flash / Redpoint - tapping either instantly creates a dated log entry (that's the send). Redpoint additionally prompts for attempt count. Comments/video/photos can be added to that log entry afterward. Separately: a log entry can be created without sending, labeled 'project' (tracks ongoing attempts), or a route can be flagged 'todo' (bucket-list, not yet tried) - both map to existing logStatusValues.
- (decision) Gamification interaction (climax beat): tapping Flash shows an immediate popup - count of routes flashed at that grade, incrementing +1 (e.g. 'flashed 6a+ x5'). User explicitly says the exact gamification treatment can be optimized/iterated later - capture the interaction, not a final visual spec.
- (decision) Journey (at home, desktop, planning) - Joel: plans a weekend boulder trip to Magic Wood. If the area doesn't exist, searches its real-world location (geocoder), creates the area there, adds the sector he'll visit. Pre-adds boulders he's scouted beforehand into that sector, each by its own exact location if known - else it displays at the parent sector/area's location. Confirms: area location is always required; sector/climb location is optional with fallback display. New schema gap flagged: climbs currently have no lat/lng column at all (only areas/sectors do) - needed for 'exact boulder location' to work.
- (decision) Personal log browsing: filterable by status - sends (flash+redpoint), flashes only, projects, todos/bucket-list.
- (decision) Area page IA: clicking/searching an area opens its area page directly. Layout: map docked to the right by default; a panel-expand control can hide the map and show area+sectors+routes filling the space instead. Two list modes: flat (all routes/boulders in the area, no sector grouping) or grouped-by-sector (small sector label per route). Default sort: hardest difficulty first.
- (decision) Route detail shows: difficulty, photos/videos linked to it from Joel AND from other group members, and which group members have flashed it. A scoping toggle exists to show only your own activity/media vs. the whole group's - not always everyone mixed together by default.
- (decision) Personal stats page IA: Achievements section (biggest flashes/redpoints - hardest grades sent), a sends-by-difficulty-grade statistic (breakdown/count per grade bucket), an open-projects section, and a bucket-list/todo section.
- (decision) Accessibility: grade badges (5a...8a) are color-coded by difficulty tier for quick visual scanning, but the text label is always present too (color is never the only signal) - palette must stay colorblind-safe. Consumer-grade stakes chosen explicitly, so this is a real accessibility-floor item, not skippable.
- (decision) Grade badge color tiers (user-specified, exact): 4a-5a+ light green, 5b-5c+ dark green, 6a-6b yellow, 6b+-6c+ orange, 7a-7b blue, 7b+-7c+ violet, 8a-9c+ black. Confirms the French grade enum's real range is 4a through 9c+ (standard a/a+/b/b+/c/c+ increments per number), not just the illustrative 5a-8a mentioned earlier. Exact hex values to be chosen at DESIGN.md token finalization, keeping each tier distinguishable for colorblind users and the black tier legible (needs light text/border against it).

What remains is applying it (schema.ts change, SPEC.md/architecture update), not deciding it.
