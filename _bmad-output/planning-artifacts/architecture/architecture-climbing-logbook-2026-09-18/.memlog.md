- (decision) [ADOPTED] Frontend rewrite target: SvelteKit + shadcn-svelte, replacing Angular 22 apps/web entirely, plain web app (no native/PWA), simplicity-biased for v1. Source: brainstorm-intent.md
- (decision) Rendering mode: static SPA (ssr=false / adapter-static). Browser calls apps/api directly cross-origin with credentials:include cookies, same topology as the current Angular SPA. Prevents: a second Node SSR process and server-side cookie-forwarding complexity that v1 has no use for.
- (constraint) [ADOPTED] apps/api response envelope: success = raw resource JSON (object or array, no wrapper), 201 on create, 204 no body on delete; error = {error: string} with 400/401/404. Frontend API client must handle this uniformly, not per-call.
- (decision) Frontend starter/tooling: scaffold apps/web fresh via official Svelte CLI (sv create, SvelteKit 2 + Svelte 5 runes + Tailwind 4), components via official shadcn-svelte CLI (copies source in, same philosophy as spartan/ui). No third-party community starter template. apps/web reused as the path (Angular deleted from it), not a new apps/web-svelte folder.
- (decision) Error format: RFC 9457 Problem Details (application/problem+json: type/title/status/detail/instance + extensions), replacing apps/api's current ad-hoc {error: string} shape across every route.
- (decision) API docs: @hono/zod-openapi (official, code-first) + @hono/swagger-ui for browsable interactive docs. apps/api routes migrate from plain Hono() + manual body validation to OpenAPIHono() + createRoute() with Zod request/response schemas.
- (decision) Shared types: new workspace package packages/contracts holding Zod schemas per entity (Area, Sector, Climb, Tag, LogEntry, Media) plus the Problem Details schema. Base shapes generated from packages/db/src/schema.ts via drizzle-zod (createSelectSchema/createInsertSchema) so the Drizzle schema stays the single source of column shape. apps/api uses these schemas for validation + OpenAPI; apps/web imports them for typed API responses.
- (constraint) apps/web (and any future non-api-server consumer) must never import @climbing-logbook/db, even type-only: packages/db/src/client.ts opens a live Postgres connection and throws without DATABASE_URL as an import-time side effect of the barrel export. packages/contracts exists specifically to have zero DB/runtime dependency for this reason.
- (decision) State management for server data: plain Svelte 5 runes (/) plus one hand-written API client module. No query library (e.g. @tanstack/svelte-query) for v1 - small data volume, few users, that machinery isn't earned yet.
- (decision) E2E/test strategy: two tiers, not a backend mock mode. (1) Pure frontend/component tests use Playwright network mocking (page.route on /api/**), zero apps/api involvement. (2) Full-stack e2e run against a real apps/api + real Postgres with NODE_ENV=test, seeded with a small fixed set of named test users by extending packages/db/src/seed.ts.
- (decision) Simplified test login: POST /api/auth/dev-login (pick a seeded user, no password) is conditionally REGISTERED on the Hono app only when NODE_ENV !== 'production' - the route does not exist at all in a production instance, not just runtime-rejected. Reuses the existing NODE_ENV check already used in auth.ts for the session cookie secure flag; no separate APP_ENV introduced.
- (decision) i18n: Paraglide JS (SvelteKit's current recommended, compiled/type-safe i18n lib). Locales: German (default), English, French, runtime-switchable. apps/api never localizes: Problem Details 'type' stays a stable English machine-readable identifier; the frontend maps known 'type' values to localized Paraglide messages. No Accept-Language handling on the backend.
- (decision) Static file serving: apps/api serves the built SvelteKit static output directly (Hono/@hono/node-server static-file middleware) mounted at '/', while /api/* stays the JSON API. One process, one container - no separate nginx/Caddy static/proxy container.
- (question) Deferred: TLS termination / exposing the self-hosted instance beyond localhost (reverse proxy, cert management) is a hosting-environment decision for whoever stands this up, not core app architecture. Revisit when someone actually deploys it beyond local/LAN use.
- (constraint) [ADOPTED] Ownership model: areas/sectors/climbs/tags are shared-editable - any authenticated user may create/edit/delete them (no per-owner check), matching 'small group of friends' scope. log_entries are per-user-owned - update/delete require eq(userId, currentUser.id) (see routes/logs.ts). A builder adding ownership checks to areas/sectors/climbs, or removing the ownership check on logs, would silently change this model.
- (constraint) [ADOPTED] Wire format casing: API JSON uses camelCase keys (Drizzle's JS-side field names, e.g. howToGetThere), db columns are snake_case - Drizzle maps this automatically. No separate case-conversion layer needed in packages/contracts.
- (question) Deferred: pagination/advanced filtering beyond simple query-param equality filters (see logs.ts climbId/userId filters) - personal-scale data volume doesn't need it for v1, revisit if the group/dataset grows.

- (decision) AD-17 Group membership via invite-or-create (user-requested, resolves the registration-gating open question). groups gains inviteCode (unique, regenerable text). Registration accepts optional inviteCode: absent -> create a new group, caller becomes its only member; present and valid -> join that group; present and invalid -> 400 error, never a silent fallback to creating a new group. One group per user for v1, enforced at the app layer only (not a DB unique constraint), so lifting it later to allow multi-membership is an app-code change, not a schema migration. Any group member can regenerate their group's invite code, atomically invalidating the old one. Supersedes AD-15's 'v1 bootstraps exactly one group, every registration auto-joins it' - multi-group creation is now real v1 behavior, not schema-only.
- (decision) AD-18 Containerized deployment (user-requested, resolves the deployment-mechanics open question - 'as easy as possible, containerized'). Multi-stage Dockerfile: build stage compiles packages/db, packages/contracts, apps/api, and apps/web (SvelteKit static output); final stage is a slim node:22-alpine runtime with only apps/api's compiled output + apps/web's static build + production deps, running node dist/index.js (which also serves the static files per AD-12). Migrations run automatically on container startup before the HTTP server binds - safe because this is a single-instance self-hosted deploy, no multi-replica race to guard against; this is what makes 'docker compose up -d' the whole deploy story. docker-compose.yml gains an app service: depends_on postgres with a healthcheck condition, env (DATABASE_URL, API_PORT, NODE_ENV=production, UPLOADS_DIR), and a named volume for uploads persisted the same way postgres_data is.

- (decision) AD-19 Grade enum + climb location/length fields (resolves CAP-3 amendment). climbs.difficulty becomes a constrained enum column (climbGradeValues as const, matching the existing climbKindValues/logStatusValues pattern already used in schema.ts) spanning 4a through 9c+ in standard a/a+/b/b+/c/c+ increments, shared by routes and boulders. climbs gains nullable length (integer, meters; UI shows it conditionally for kind=route, always null for boulders - no separate boulder/route tables) and nullable latitude/longitude (doublePrecision, same pattern as sectors/areas) - when a climb's own location is unset, the frontend displays it at its parent sector/area's location, this is a display fallback, not a DB default. packages/contracts' drizzle-zod-generated Climb schema picks this up automatically (AD-6) - no separate contracts change needed.
- (decision) AD-20 App-content search (resolves CAP-11). A dedicated apps/api endpoint (GET /api/search) - not client-side filtering - because search must cover the caller's whole group, not just whatever's currently loaded in the active view. Case-insensitive substring match (ILIKE) on area/sector/climb name, plus exact match on the new grade enum for difficulty search; no full-text-search extension (pg_trgm/tsvector) - unneeded complexity at this data scale. Must reuse AD-15's requireGroupMember helper - results are scoped to the caller's group, same as every other area/sector/climb read.
- (decision) AD-21 Gamification/achievements computed live, no new table (resolves CAP-12/CAP-9's Achievements needs). Per-grade flash count and the stats-page Achievements section are both live COUNT/query results against existing log_entries (joined to climbs for grade) - never a maintained/denormalized counter column, consistent with AD-15/AD-16's established house style of preferring a live join over a copy that can drift. Data volume at this app's scale makes the query cost negligible.
- (decision) AD-22 Geolocation-based area suggestion (resolves CAP-10). Client-side only: Haversine distance between the device's current position and each area in the caller's already-fetched group area list (typically a handful of rows); areas within a configurable default threshold (~2km) are suggested. No new backend endpoint, no server-side geo query/index - reuses AD-1's existing browser Geolocation capture and the area list the client already holds.
